When working in a collaborative development environment, having decoupled, modular code architecture is absolutely paramount. Otherwise, it is, in essence, impossible to work with each other without constant and impeding communication as, without it, disastrous code merges will occur. While "hacking things together" can initially work and, indeed, this is an important part of the iterative design process, it's of equal importance that a programmer takes that logic and functional code and splits it in such wise that, while still dependent of each other, each section exists in separate files. Let's say that two programmers on the same project are each working independently on a health and movement system. If both of these systems are being written on the same file, when the two of them merge their work together, they're essentially now merging two almost completely different files. For example, the code that each of them has written could occupy the same line space in the file, and when merged the two differing uses of that space overwrite each other; a so-called "disastrous merge conflict." 

Additionally, this kind of code structure can lead to greater issues with debugging as with a modular code structure, a programmer can be assured that any issues with their code exist in isolation from the rest of the database. If everything is coupled together, the programmer will have to parse through much more code, a lot of which won't be their own work, in order to identify problems, and the modifying of that code having the potential to break other functionality.
